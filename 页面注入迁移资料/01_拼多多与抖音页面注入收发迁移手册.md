# 拼多多与抖音店铺：页面注入收发迁移手册

整理日期：2026-10-02。源码来源：`D:\云监控\app` 的当前磁盘文件。

本次只提取源码、编写迁移资料和执行隔离的本地测试；生产程序、店铺开关、登录会话保持原样。本包没有复制 Cookie、账号配置、聊天数据库、运行回执或真实订单数据。

## 1. 先看结论：两平台的实际路径不同

| 路径 | 收消息 | 发消息 | 迁移定位 |
|---|---|---|---|
| **拼多多当前默认 guest 路径** | Electron guest 的 CDP `Network.webSocketFrameReceived` → Titan 解包 → 标准化 | 同一个已登录 guest 页面内执行脚本，调用页面签名器，再 `fetch` | 优先迁移；是“CDP 接收 + 页面上下文发送”，不是全程纯 Store 注入 |
| 拼多多可选 Chrome 路径 | Playwright WebSocket 监听 + `yz-pdd-hook.js` 读取 Vue Store / IMSDK 队列 | 页面 `IMSDK.sendCmdMsg` 或页面 `fetch` | 保留的可选路径；与默认路径有差异，迁移前单独验证 |
| **抖音飞鸽路径** | 页面 `__monaGlobalStore` 中的 Store、IM 事件与历史扫描 → 宿主轮询取出事件 | 同 frame 内 `im.chatWithUid()` → `im.sendText()` | 页面注入桥；宿主仍负责去重、合并、人工暂停、持久化 |

**复制一个 JS 文件并不等于完整接入。** 接收、发送、登录分区、宿主桥、去重、回执、人工暂停是一个整体。目标软件若不是 Electron，需要补齐同等宿主能力，再移植平台逻辑。

这些是平台页面内部接口，不是平台公开稳定 API。本文描述当前代码与既往测试证据；截至整理日，没有重新验证真实平台的新版本。

### 依赖闭包

`PddAdapter` 直接 import `PddChromeBridge` 和 `pddOrderProbe`。即使只选默认 guest 路径，也应先复制这些文件以保持编译闭包，或在目标项目里明确拆除相应 import / 分支。`pddGuestSender` 的结果类型也来自 `pddChromeBridge`。

核心依赖：Electron 的 WebContents / WebFrameMain、Node 的 fs / path / zlib、浏览器的 fetch / TextEncoder / crypto.subtle。可选 Chrome 路径另需 `playwright-core` 和本机 Chrome。

原项目版本记录：Electron `42.8.1`，TypeScript `^5.9.3`，Playwright Core `^1.63.0`，Vitest `4.0.14`。这些是当前 package.json 的声明，不代表迁移软件必须逐项同版。包清单和锁文件均附于源码快照，用于核对原环境。

原项目使用 `@shared` 路径别名。目标项目需要配置 TS 与构建工具的同名 alias，或替换为相对 import。Vue / Pinia / Element Plus 是原宿主 UI 依赖，并非页面收发算法本身的必要依赖。

## 3. 宿主软件应具备的能力

### 3.1 最小宿主接口

```ts
interface PageHostCapabilities {
  // 在已登录商家页面的 MAIN world 执行，返回可序列化结果；等待 Promise 完成。
  evaluateMainWorld<T>(script: string, frameId?: string): Promise<T>
  // 列出真正承载 Store / IM 的页面 frame，保留用于发送的 frame 身份。
  listFrames(): Promise<Array<{ frameId: string; url: string }>>
  // 拼多多默认接收路径需要；文本帧原文，二进制帧按 CDP 约定传 base64。
  onWebSocketFrame(listener: (payloadData: string, opcode: number) => void): void
  // 为自动发送 / 人工发送归属判定提供请求观察能力。
  onRequest(listener: (url: string, postData?: string) => void): void
}
```

上面是移植接口示意，不是原项目已实现的新抽象层。Electron 里分别对应 `executeJavaScript`、`WebFrameMain` 和 `guest.debugger`。

### 3.2 执行世界与 frame

- 页面 Store、IM、签名器属于商家页面 MAIN world。目标软件的 isolated-world preload、扩展 content script、普通跨域 iframe 访问与此不同。
- 插件 / 扩展宿主若使用隔离世界，应通过其 MAIN-world 执行能力或页面消息桥连接，桥消息加入来源校验和 schema 校验。
- 抖音应在发现 Store / IM 的那个 frame 里发送；在顶层壳页运行同一段脚本可能读不到对象。
- 当前抖音只检查主 frame 和其直接子 frame，深层 iframe 是迁移时的检查项。
- 拼多多默认脚本针对顶层 Vue2 `#app.__vue__.$store`，其可选 hook 有 Vue3 探测逻辑；这不等于默认发送器也覆盖 Vue3。

### 3.3 登录与页面隔离

原入口：

```text
拼多多 https://mms.pinduoduo.com/chat-merchant/index.html
抖音   https://im.jinritemai.com/pc_seller_v2/main/workspace
拼多多 partition = persist:pdd-store-default
抖音   partition = persist:douyin-store-default
```

每家店铺应有稳定、独立的 `profileId`、persistent partition、运行状态文件、恢复水位和发送队列。登录 Cookie 留在对应 session，签名和发送也使用同一 session / 页面。

原宿主设置 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、`webSecurity: true`；guest 不装载宿主 preload，不向商家网页暴露文件系统或任意 IPC。初始地址和后续导航使用 HTTPS 域名白名单，窗口弹出默认关闭。

原 `main/index.ts` 用“是否等于抖音默认 session”判断平台，其他 guest 都进入拼多多适配器。这适用于当前两个默认分区；多店迁移应改成 `partition → platformId/profileId/adapter` 显式映射。

设置 userData 根目录发生在 `app.whenReady()` 和 session 创建之前。迁移登录数据需关闭相关程序、完整备份并验证；Cookie 存在并不等于平台会话仍有效，过期或被服务端撤销仍需重新登录。

## 4. 拼多多默认 guest 路径

### 4.1 接收链路

```text
PddAdapter.attach(guest)
  → guest.debugger.attach('1.3')
  → Network.enable
  → Network.webSocketFrameReceived
  → decodeTitanPayload(payloadData, opcode)
  → extractPddCandidates(payload)
  → normalizePddCandidate(candidate, profileId)
  → processMessage / 订单卡辅助查询
```

Titan 解码器的实际能力：文本 JSON；二进制帧 base64 解码；搜索 `1f 8b 08` gzip 头，处理前后包裹字节，再尝试 JSON。它是启发式解析，不是完整 protobuf schema 解码器。

标准化依据：`from.role === user` 是买家；`from.role === mall_cs` 是商家；`msg_id` 是去重主键；`ts` 统一为毫秒；`seq_id` 作为平台序列。买家 ID 从消息方向对应的 uid 取得，而不是从当前 UI 选中会话猜测。

当前默认 `processMessage` 只自动回复非空文字。商品链接、订单卡、图片、撤回、系统事件可被识别或用于采样 / 查询，但没有统一的多模态自动回复流水线。接收去重与同文判断分开：相同文字但不同 `msg_id` 应视为两条消息。

**仅监听模式的现状：** 默认 CDP 帧分支在自动回复关闭时仍做订单辅助处理，但一般消息跳过后续 `onMessage` 回调；可选 Chrome hook 分支在关闭时仍可调用 `onMessage`。另一个软件若需要“关闭自动回复仍记录所有收到的消息”，应把观察与处理开关明确拆开。

### 4.2 发送链路与请求字段

```text
同一 guest.executeJavaScript(createPddGuestSendScript(input), true)
  → 确认 origin、mall_id 与页面 signer
  → updateServerTime / messagePack
  → 正文 UTF-8 SHA-256
  → 页面 fetch(credentials: include)
  → 业务成功 + 正式 msg_id
  → 保存回执
```

签名器探测顺序：

```js
window.riskControlCrawler
  || store.state.riskControlCrawler
  || store.state.IMSDK?.riskControlCrawler
```

发送地址：`https://mms.pinduoduo.com/plateau/chat/send_message`。

核心字段：`cmd: send_message`、`client: WEB`、`to.role: user`、`to.uid: buyerId`、`from.role: mall_cs`、`type: 0`、`msg_id: null`、`is_aut: 1`、`manual_reply: 0`、`pre_msg_id` 使用触发回复的入站消息 ID。

`anti_content` 在 `data` 和请求外层各放一份，header 也带 `anti-content`。签名实时调用页面生成，长度不是固定常量；既往见过的长度 423 不应写成校验标准。`Cookie/Origin/Referer` 随同页浏览器请求处理，不需要从主进程复制后重造。

**默认发送器的 `hash` 是回复正文 UTF-8 的 SHA-256 十六进制值。** 可选 Chrome 分支保留过另一个计算口径，两个口径分别记录在原源码中，迁移时以选定路径为准。

现有成功判定同时要求：

```text
HTTP response.ok
data.success === true
result.result === 'ok'
result.msg_id 非空
```

`pre_msg_id` 返回与传入不同会留下提示，但正式 `msg_id` 已取得时仍标为 accepted。`status: read` / `is_read: 1` 是请求字段，不是买家已读证明。

### 4.3 去重与人工介入

- `PddStateStore.claimMessage(msg_id)` 在发送前落盘，单个适配器内 Promise 队列顺序处理。
- 商家出站 msg_id 若能在本程序回执中找到，则识别为本程序回显；其他商家消息触发会话暂停。
- 额外观察 `/plateau/chat/send_message`：`manual_reply === 1 && is_aut !== 1` 判定人工发送；同买家 / 同文本的程序发送标记用于避免误判。
- 回复宽限默认 1200 ms，发送前复查开关、会话暂停与 generation；已经进入网络发送阶段的请求不具备撤回式取消能力。
- 页面 readiness 探测“有 Store / signer”不是完整 WebSocket 健康探测。UI 显示在线、页面出现气泡和买家实收应分层描述。

### 4.4 拼多多可选纯页面接收 hook

`yz-pdd-hook.js` 暴露 `window.__YZ_PDD_HOOK_V1__`：`rescan()`、`drain()`、`pending()`、`status()`。首次运行扫描 Store，随后 Vuex mutation、IMSDK `options.onmsg` 包装和每 400 ms 扫描共同补获消息；宿主每 250 ms drain。

此 hook 在原代码中由 **PddChromeBridge** 装载，不是默认 Electron guest 接收器装载。宿主若把它装到自己的 webview，需另写事件轮询接线；默认适配器不会仅因全局对象存在就自动消费。

原 hook 启动约 8 秒热身，扫描到的消息先加入 seen 而不 enqueue，旧消息和热身期新消息可能被视为已见。它只保留简化文字字段，`info/biz_context` 卡片字段会被裁掉；卡片能力应使用 CDP 原候选或扩展保留字段。

可选 Chrome 宿主是 `launchPersistentContext` 打开独立 Chrome profile，不是 `connectOverCDP` 连接任意已打开 Chrome。profile 路径来自 `PDD_CHROME_PROFILE` 或 `_capture/chrome-profile`，迁移后应显式配置。

## 5. 抖音飞鸽页面桥

### 5.1 页面对象与接收

```js
const context = window.__monaGlobalStore?.data?.initContextData
const im = context?.im
const store = context?.Store?.instance
```

桥对象：`window.__yunzhishouDyBridge`。宿主 `DouyinAdapter` 每 1500 ms 在候选 frame 执行 `DOUYIN_BRIDGE_SCRIPT`；脚本重复执行时复用同一 IM 实例的桥，返回 readiness、历史任务状态、verifiedAt 和事件数组。

接收来源：`im.onMessage`、`im.onMessageChange`，以及 Store 的 `conversationMap`、`messagesByConversationId` 和 conversation.lastMessage。`sender_role: '1'` 是买家，`'2'` 是商家；`serverId` 优先、`id` 兜底；conversation 与 buyer 都取得后才入事件队列。

事件主要形状：

```ts
type PageEvent =
  | { kind: 'message'; source: 'live' | 'history'; buyerId: string;
      conversationId: string; message: Record<string, unknown> }
  | { kind: 'manual'; buyerId: string; conversationId: string; at: number }
```

桥保留文本、时间、角色、客户端 ID、goods_id/order_id 和部分 card ext。不是完整原始对象；桥里没有保留 `pigeonMsgType`，而标准化器优先读该字段再读 ext.type，因此平台新增类型时应检查字段保留与类型判定是否同步。

### 5.2 历史补偿与合并

- 页面扫描至多 250 个会话和各组最后 30 条消息。
- 每 15 秒最多对 6 个候选会话轮询尝试历史拉取，单会话至少间隔 8 秒。
- 历史函数名和参数目前是探测式尝试；“某方法有返回”与“完整同步成功”是不同概念。
- 宿主先等待历史 pending 结束，排序再处理；超过 20 秒暂停自动回复。
- 水位窗口：最后在线时间前移 5 秒，最多回看 24 小时；首次基线只取当前时间前 5 秒。
- 持久去重键 `dy:${profileId}:${platformMessageId}`；**开关关闭时收到的入站消息也会被 claim，开启后并不默认补回这些消息。**
- 同会话 3500 ms debounce 合并文字；不同买家独立 bucket，但实际发送用一个串行队列，避免 `chatWithUid` 切会话造成串单。

这不是完整历史归档系统；队列截断、扫描范围、方法兼容性、断线时间较长都会影响补偿范围。

### 5.3 发送与回执

```text
activeFrame.executeJavaScript(douyinSendScript(buyerId, text, receivedAt))
  → bridge.send
  → await im.chatWithUid(buyerId)
  → 核对当前买家与 conversationId
  → 核对 manualAt
  → im.sendText(conversationId, text)
  → 读取原生响应
```

桥内成功判定：

```text
serverId 非空
Number(flightStatus) === 3
Number(serverStatus) === 0
ext['s:send_response_status'] === '0'
ext['s:send_response_check_code'] === '0'
```

这是当前响应结构的判定口径，平台升级后需重新检查。

**抖音路径没有拼多多的 `is_aut` / `manual_reply` 请求组装。** 直接调用飞鸽页面自己的 sendText，具体底层标记由平台 SDK 处理；此处没有验证自动身份标记字段，也没有把拼多多字段硬塞到抖音 SDK。

### 5.4 人工回复识别

桥包装 `im.sendText` 并保留原函数的 this / args。桥自身同步调用原生发送时设置 `ownSend`，其他调用产生 manual 事件与时间戳。宿主对 manual 持久暂停该会话、清除合并计时器、增加 generation。

历史中发现晚于待回买家消息的商家消息会取消该批回复，但这与“收到人工 sendText 事件后持久暂停”是两种机制。其他插件、官方自动回复、另一个商家端可能绕过 wrapper；一个 wrapper 的覆盖范围有限，迁移时应补测。

## 6. 套入另一软件：操作顺序

### 6.1 Electron 目标项目

1. 从 `源码快照/` 复制核心文件并配置 `@shared` alias；先保持原依赖闭包。
2. 建立每平台 / 店铺独立 partition 与状态目录；不要复制导出包以外的旧真实登录数据当作源码。
3. 在宿主 guest 创建完成时，按显式 partition registry 调用对应 adapter.attach。
4. 用目标软件自己的规则、消息入库和 trace 服务实现 `getRules/onMessage/onTrace`；原 registry 只作为接线参考。
5. 初次接入显式关闭自动回复，并确认存储旧设置不会在 attach 后恢复开启。
6. 只读验证页面、买家身份、消息 ID、类型、方向与 frame；随后在测试店铺启用固定回复验证。
7. 接入运行状态、开关、人工暂停恢复 UI；成功提示区分服务端接受、商家回显和买家实收。

下面是适配器实例化示意，**没有实现完整宿主创建、鉴权 IPC 或业务规则**：

```ts
import { join } from 'node:path'
import type { WebContents } from 'electron'
import type { GeneralSettings, Intent, BannedWord,
  NormalizedMessage, MessageTrace } from '@shared/contracts'
import { PddAdapter } from './integration/pddAdapter'
import { DouyinAdapter } from './integration/douyinAdapter'
import { PddStateStore } from './integration/pddStateStore'
import { DouyinRecoveryState } from './integration/douyinRecoveryState'

type Rules = { intents: Intent[]; bannedWords: BannedWord[]; settings: GeneralSettings }

async function bindShop(input: {
  platform: 'pdd' | 'douyin'; profileId: string; stateDir: string; guest: WebContents;
  getRules(): Rules; onMessage(message: NormalizedMessage): void;
  onTrace(trace: MessageTrace): void;
}) {
  // stateDir 应由宿主按稳定店铺标识分配；profileId 不直接拼入未校验的文件路径。
  const stateStore = new PddStateStore(join(input.stateDir, 'runtime-state.json'))
  const common = {
    profileId: input.profileId, stateStore,
    getRules: input.getRules, onMessage: input.onMessage, onTrace: input.onTrace
  }
  const adapter = input.platform === 'pdd'
    ? new PddAdapter(common)
    : new DouyinAdapter({ ...common,
        recoveryState: new DouyinRecoveryState(join(input.stateDir, 'recovery-state.json')) })
  if (input.platform === 'pdd') await stateStore.setAutoReplyEnabled(false)
  else await (adapter as DouyinAdapter).setAutoReply(false)
  await adapter.attach(input.guest)
  // 同一 guest 仅绑定一次；之后由受控 UI 在 online 后开启自动回复。
  return adapter
}
```

此示例每次 bind 都关闭开关，用于首轮接入测试；上线时可自行设计显式的恢复策略。拼多多选择 guest 模式需在初始化前确认 `PDD_SEND_CONTEXT !== 'chrome'`。默认 guest 路径依然使用 CDP 接收，不应遗漏 Network 监听。

### 6.2 非 Electron 目标项目

CEF / WebView2 / 浏览器扩展 / 浏览器自动化框架需要替换 Electron 的 host 部分。页面脚本、字段标准化和业务状态逻辑可以作为复用起点，但 CDP 接口、MAIN-world 执行、frame 身份、session 目录和序列化回传应由对应宿主实现。

抖音最先可迁的是 `DOUYIN_BRIDGE_SCRIPT` + `douyinSendScript` + 标准化器；拼多多最先可迁的是默认页面发送脚本 + Titan 解码器。为统一纯页面接收而使用 `yz-pdd-hook.js` 时，要额外修正热身消息处理、卡片字段、事件清理和宿主队列消费。

## 8. 已发现的迁移注意事项

### 8.1 消息成功分层，避免再次出现“页面显示发了，手机没收到”

1. `调用开始`：程序进入发送阶段。
2. `服务端接受`：业务成功并返回正式平台消息 ID。
3. `商家回显`：收到平台出站消息且与自己的回执匹配。
4. `买家确认`：真实买家端可见，或另有经验证的到达回执。

四层应分开。买家未读不等于未到达；本地气泡和 HTTP 200 也不等于服务端接受。当前 buyerConfirmedAt 来自人工核验 API，并非平台自动证明。

### 8.2 去重不是完整 exactly-once 保证

当前 JSON 存储先 claim 后发送；发送失败的消息已进入 processed，默认没有持久重试 outbox。进程在 claim 与回执之间崩溃也可能留下缺口。processed 只保留最近 10000 个，receipts 2000 个，超出窗口的旧消息可能再次被处理。

JSON 写盘为串行 writeFile，不是临时文件原子 rename，也没有跨进程文件锁；读盘异常回到空状态可能导致历史去重记录丢失，写盘失败还可能让 writeQueue 持续失败。迁入正式产品建议用事务存储，明确 `received → processing → accepted/failed/unknown` 状态与恢复策略。

结果不明确时先按平台 msg_id / 记录查询核对，再决定重试。可选 Chrome 的 IMSDK 尝试后落到 fetch 的策略存在“首次已接受但回执不明确”时双发风险。

### 8.3 人工暂停边界

- 自己的出站回显早于回执落盘时存在归属竞态，应加入在途发送登记或 client ID 匹配。
- 外部自动工具发送会与人工发送混杂，建议同一店铺测试时只启用一个自动回复源。
- 原 PDD 的 request 标记、原 DY 的 wrapper 是实际实现，不是所有平台入口的全覆盖证明。
- 抖音 `ownSend` 标记只覆盖 sendText 的同步调用阶段，SDK 内部异步重入是额外测试项。
- generation 主要取消尚未提交的任务，不是网络请求提交后的撤回工具。

### 8.4 生命周期与资源

- PDD hook 有 timer / subscribe / 函数包装，但没有统一 dispose；抖音桥同样没有完整 unsubscribe / 原函数恢复。
- SDK 实例替换、同页面重复装配、guest 重绑定应检查是否重复监听。PDD adapter 的生命周期监听也需由宿主保证一 guest 一 adapter。
- Chrome 分支有自己的长期 context / poller；退出与重绑定清理需补齐。
- Titan gzip 的首次解压没有输出大小上限，回退搜索也有成本；迁移时增加输入 / 输出大小和 CPU 时间约束。
- 页面脚本或 fetch 卡住会影响串行发送；默认 PDD 发送没有独立 AbortController 超时。订单只读查询另有 10 秒超时。
- backgroundThrottling 设为 false 只是原宿主配置，最小化、休眠、断网、页面重载与登录过期仍需验收。

### 8.5 消息内容与业务规则

- ID 按字符串传递；超长数值 ID 先经过 Number 会丢精度。
- 注入脚本入参保留 `JSON.stringify` 编码，不用文本直接拼进 JS 字符串；测试引号、反斜线、换行、emoji。
- 回调 onMessage / onTrace 里的存储或 UI 异常应隔离，避免影响下一条收发。
- 固定回复器是子串关键词匹配；空 / 全空白关键词会匹配所有文字，应在导入规则时过滤。
- `orderStatus`、商品 scope、优先级之外的复杂业务条件未被当前 resolver 完整使用。示例“默认中通”等是原规则样例，迁移店铺需要替换为真实经营事实。
- 当前适配器 trace 明确 `llmCalled: false`，没有直接调用 Jev 或大模型；需要另接处理层。
- 当前 PDD `is_aut=1` 已落实，但“首条强制智能客服身份说明”不在发送器或固定回复器里统一强制，目标处理层应显式实现。
- 收到媒体 / 卡片与读懂内容是两件事；本包没有图片识别、视频理解、完整商品 SKU 采集或抖音订单详情 API。

### 8.6 数据与诊断

**源码是静态代码，运行数据另行保护。** 迁移无需把 Cookie、anti_content、手机号、地址、整段响应体写到日志。

现有可选 Chrome `writeJsonLine` 诊断含 buyerId、text 和 responseBody / 入站 content 等值，不是全量脱敏日志；路径在 `%APPDATA%/Electron/pdd/`，迁移时应关掉或脱敏并改成目标软件受控目录。存储回执本身也含买家标识，设置访问权限与保留期限。

字段形状采样与原始调试日志分开看待；对象字段名也可能含动态标识，结构诊断同样需审查。导出包只含静态源码及合成测试，不包含这些运行日志。

当前核心路径没有修改 navigator.webdriver / plugins / language、没有改 visibilityState / visibilitychange、没有自动点掉等待提示。本包也不添加这类操作；是否产生自动化可观察特征应单独评估，页面上下文发送不等于对平台不可见。

## 9. 实测范围与迁移验收

### 已有证据（既往用户参与的真实店铺测试，非本次复测）

- 拼多多、抖音：固定文字回复买家实收，多买家分别回复，人工介入暂停等流程已有通过记录。
- 抖音：非当前选中的买家会话回复已有测试，连续消息合并已有测试。
- 拼多多：订单查询非空与 0 笔、买家间结果隔离、商品标题规格对照已有测试。
- 本次离线测试与字节一致性结果单列在 `04_源码清单与校验.md`，不要混同真实平台验收。

### 在目标软件应重新做的最小验收

| 用例 | 期望 / 核对 |
|---|---|
| 首次登录，重启目标软件 | 店铺 session 可复用或明确显示登录过期 |
| 自动回复关闭时发送测试消息 | 观察行为清晰；目标软件若需全量记录应验证已拆分观察与发送开关 |
| 一个买家文本 | 返回正式 msg_id / serverId，买家实收 1 条 |
| 同文字连续两次 | 按两条不同平台 ID 记录，合并策略按平台说明生效 |
| 同一 ID 重复推送 | 处理和发送只发生一次 |
| A/B 买家，商家页停留 A | B 被识别并回给 B，不串会话 |
| 人工先发，随后买家问 | 持久暂停；刷新 / 重启后仍符合暂停策略 |
| 发送即刻切换会话 / 关闭开关 | 发送前校验取消仍待提交的任务 |
| 页面刷新 / SDK 更换 / 登录失效 | 恢复桥或明确禁用发送，不重复装载多个监听器 |
| 短断网 / 休眠 / 重启期间消息 | 记录补偿范围与未覆盖缺口，不宣称全部补回 |
| 平台拒绝、超时、缺正式 ID | 显示 failed / unknown，先核验再重试 |
| 包含引号 / 换行 / emoji | 脚本参数编码正确，文本不串入 JS |
| 新店铺 / 子账号 / 多店 | 身份、权限、分区、状态文件与买家 ID 全部隔离 |

建议先用每平台一个测试店铺验收，文字链路通过后再接复杂回复、订单业务与多店并发。
